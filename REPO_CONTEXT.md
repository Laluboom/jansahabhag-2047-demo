## Read this first

This repository contains a frontend-first interactive demo of JanSahabhag 2047, a fictional civic learning and participation platform. The user’s original goal was to implement the product described by `README.md` and `IMPLEMENTATION_PLAN.md` using the sub-agy Autobuild method. The user later **explicitly paused** that goal. Before any new implementation, read [paused.md](paused.md): it identifies the precise Git branch and job state, quota stop, verified pending branch, remaining plans and resume sequence. The product documents describe intended scope; this file describes the code that exists at the pause.

The central story is Aarav Sharma, a 17-year-old at Navchetna Public School in Jaipur, working through “My Community, My Future” on safer pedestrian crossings near schools. The participant path should connect learning, a field assignment, teacher verification, evidence-backed Youth Assembly deliberation, a structured proposition, reflection and a Civic Passport. Seven seeded personas expose participant, teacher, facilitator, institution, programme and platform perspectives. All names and data are fictional. The app is deliberately a browser demo: no backend, real authentication, live AI, real-time collaboration, video or external delivery service exists.

## Repository shape and app boot

This is one React 18, TypeScript and Vite package. `index.html` loads `src/main.tsx`, which renders `src/app/App.tsx`. The app initializes `useAuthStore`, then renders the browser router from `src/app/router.tsx`. Most routes share `AppShell`, with a desktop left navigation, top utility bar, current persona label, notification access, and mobile bottom navigation. `src/components/ui/` provides controls such as buttons, cards, status chips, tabs and dialogs; `src/styles/index.css` and Tailwind configuration establish visual tokens. The prominent evidence-to-action thread motif ties the product areas together. React Router resolves participant, admin and preview routes; a not-found screen handles unknown routes.

The source is organized by user-facing area under `src/features/`: auth-demo, dashboard, learning, assignments, assemblies, propositions, passport, activities, projects, events, community, institutions, administration, moderation, analytics and previews. `src/types/domain.ts` defines the stable-ID entities and state unions. `src/types/index.ts` adds action inputs and aggregate view contracts. The seed is split into subject files under `src/data/seed/`, then assembled by `src/data/seed/index.ts`. This is the only canonical initial database. `getFreshSeedDatabase()` clones it so reset cannot mutate the seed.

## Data flow and service ownership

Screens should depend on the asynchronous `DemoRepository` contract in `src/services/repository.ts`, currently implemented by `LocalDemoRepository` in `src/services/demoRepository.ts`. UI components should not read or write `localStorage`, and should not use mock seed arrays as their live data source. The repository loads `DemoDatabase` through `PersistenceService`, applies domain actions, saves it, and returns typed records or view models. `src/stores/authStore.ts` holds only the selected demo persona and language preference; `useAppRefreshStore` helps screens reload after actions. The full database belongs in persistence, not scattered component state.

`PersistenceService` uses browser key `jansahbhag_demo_v1`. On first launch it seeds automatically. On subsequent loads it invokes `runMigrations`, which currently keeps compatible schema version 1 data or resets incompatible/corrupt data to a fresh seed. If browser storage is unavailable, an in-memory fallback keeps the current session usable, without refresh durability. The profile/top utility reset action clones the canonical seed again. A future schema change should increment `CURRENT_SCHEMA_VERSION` and update migrations; otherwise old browser data can be misread.

The repository is the product logic boundary. A lesson completion updates enrolment progress and writes a +5 Learning credit, an activity and Passport metadata. Assignment draft and submit are separate actions; submission writes +10 Contribution once. Teacher review changes the **same submission** a participant sees, marks attached evidence verified, creates +5 Observation transactions per evidence, and writes linked Passport/notification records. Invalid edits to verified or under-review submissions are rejected. Credit totals derive from ledger transactions rather than a single stored score. Evidence and Passport records use source IDs so the user can trace work across modules. The Task 03 branch extends the same pattern to assembly joins and contributions, propositions and reflections.

## Personas, privacy and simulation

`/demo-login` and utility controls switch among seeded identities, updating local `activeUserId`. This is not an authentication system. Role-aware menus and UI checks are an instructional simulation; the browser database is not a secure boundary. Participant views should filter by user ID, while Kavita Rao’s teacher queue should show eligible institutional submissions and review the selected one. Private evidence should remain in owner or appropriate review views, not on public surfaces. Do not use real participant data in the demo or claim that local verification is authoritative.

Community posts, RSVP, notifications and moderation transitions stay within the browser. Assembly peers and stages are scripted/local. Any AI text, national metrics, stakeholder engagement or multilingual tooling should be marked simulated or Demo Preview. Civic Credits represent recorded activities, not an evaluation of a person’s civic worth. Proposition support, dissent and unresolved questions must remain visible rather than being reduced to a single consensus label.

## Adding or changing a feature

Find the route in `src/app/router.tsx`, then its feature screen, the repository method it calls, and the domain type it uses. Extend the repository interface and local implementation together when adding a transition. Add/update seed records only when a representative initial state is needed. Keep action-created credits and Passport records idempotent and source-linked. Test the transition at repository level and add a screen test when it protects a real interaction. Use responsive semantic controls, visible focus and clear labels; preview controls should explain their simulated state rather than appearing broken. Keep notifications linked to valid routes.

Deployment is not configured. `README.md` names Vercel or Netlify as possible hosts, but no target or credentials were supplied. A local `dist/` can be built and previewed, yet no production URL should be claimed. [TODO.md](TODO.md) lists work still required for the demo and for any future production system.
